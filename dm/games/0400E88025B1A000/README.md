# Star Fox (`0400E88025B1A000`)

A Switch 2 game: update v131072, SDK 21.4.4 built for the Switch 2 (`Ounce`), NVN2 with DLSS. A custom engine (its own prefixes: `vfs`, `vrender`, `vjob`, `vscript`, `vspirv`, `veffects`, `vphysics`; project name `eclipse`), with Wwise 2024.1 for audio, Bullet physics and NPLN for online play. Modules `main`, `sdk`, `subsdk0` (the SDK's movie module), `subsdk3` (`nn::camera`); `subsdk1` (the C library) and `subsdk2` (`NintendoSDK_DLSS`) are shipped but `main` imports nothing from them. **Plays on the Mac** (M4 Pro, 48 GB): the title, the prologue cinematic and the tutorial flight, with sound. The tutorial runs at 56 to 60 fps with a 4K screenshot every 4 s and at 60 without them; the cinematic at 30 fps, which looks like the game's own choice (not checked). Scripted input here reached the tutorial's first lesson and worked its options menus; flying under input has not been watched on this Mac (pull request #1259's author reports 7 minutes of it with a controller on an M5 Max). **Plays on the iPhone 18 Pro Max** (X1.0, handheld): the owner played from the title through the prologue and the tutorial into Corneria, the first start with freezes of up to 2.1 s while it built its pipelines, the second at 60 fps; the app now ships the prewarm list that run recorded ([On the iPhone](#on-the-iphone)).

## What it needs

| Setting | Where | Why |
|---|---|---|
| `mem_alias 0x400000000`, `mem_reserve 0x550000000`, `mem_stack 0x10000000`, `app_pool 0x240000000` | [`game.tsv`](game.tsv) | the Switch 2's 9 GB. The alias region mapped up to +8.26 GB of its 16 GB, 6.78 GB at most at once, through the tutorial's start; 8.5 GB resident, 4 GB of it allocated on the GPU |
| `sys_resource 0x1000000` | `game.tsv` | the NPDM declares 16 MB, so virtual address memory is on; `main` never sets a heap |
| `modules main subsdk0 subsdk3 sdk` | `game.tsv` | `main` imports 17 movie functions from `subsdk0` and 19 `nn::camera` functions from `subsdk3`, nothing from `subsdk1` or `subsdk2` |
| `romfs_marker data.zip` | `game.tsv` | the RomFS has two files, and this is the game |
| `zip_store .zip:.metallib` | `game.tsv` | the archive's members are LZ4-compressed already |
| `shader_groups /data.zip=shader` | `game.tsv` | every shader is a member of the archive |
| `depth_mode zero` | `game.tsv` | the game sets near = 0 with `nvnDeviceSetDepthMode` before its first frame, so the pipeline bases made before it runs (the app's archive made offline, the Mac prebuild) need the `main0_z` vertex entries; without it a Mac app's 66.5 MB archive was refused and its first start built 1,483 bases before the first frame ([below](#found-on-this-game)) |

There is no game-specific patch, and only v131072's build row: the base game, v0, has not been run.

## Files

- A NUP container of 30 GB: a base package (v0) and an update package (v131072), each with its own ExeFS and RomFS. Neither package carries a NACP or an icon, so the name comes from the profile, the display version is the placeholder `v131072`, and the app gets the NX 18 icon (`--icon` gives it the game's).
- The RomFS is two files: `data.zip` (14.5 GB) and `veclipse_build.cvar` (a JSON line: `system.is_shipping_build: true`). `main` opens `rom:/data.zip` through its own virtual file system (`vfs.zip.c`): [LZ4-chained zip members behind a VZIP preamble](../../../docs/reference/shaders.md#lz4-chained-zip-members-behind-a-vzip-preamble-and-shader-binaries-of-one-stage). Its 114,154 members are named by a 16-digit hash with no folders or extensions; 92,069 are chained, 22,085 (the Wwise `RIFF` sound files and `BKHD` banks) stored plain.
- `main` is 192 MB of code with 1,036 imports, of which the host and the other modules supply all but two (gRPC thread-local initialisers, `_ZTH…`). No shader is in any code module.

## Shaders

2,856 in [`shader_map.tsv`](shader_map.tsv): 1,483 vertex, 1,305 pixel, 68 compute; 2,828 one per archive member, no task or mesh shaders, and the rest from the two NDSR upscaler networks embedded in `VIPR` containers. All of them translate. A build takes about 4 minutes in all on an M4 Pro. Each member is the engine's shader binary (`_vrender_shader_binary_t`), read as a single-stage program and paired at draw time (`separable_pairs`: 1,480 cover pairs).

## The picture

Docked, every 3D target was 768x432 from the first frame of the title to the tutorial: MetalFX stands in for DLSS at 768x432 to 768x432, the game's NDSR compute networks take that to 1536x864, and the result reaches the 3840x2160 swap chain, whose top-left 1920x1080 holds the picture. The game's own defaults give the reason for the figure, not the cause: `render.dynres_min_scale_x` is 0.5 and `max` 1.0, so 768x432 is the minimum of a 1536x864 base, at 6 to 11 ms of GPU time a frame on the M4 Pro. Segment timestamps (the profile key `gpu_timestamps segment` then, the host's default since) changed nothing, with the GPU's idle gaps still counted. Resolved, the cause of the docked size: the host answered graphics scale tier 1 docked, and the game renders 0.8 times smaller below tier 0 (byte +0xa of its mode event, `main+0xba69970`): 768x432 for its 1920x1080 window where tier 0 gives 960x540, its handheld size. On the Mac the host now answers tier 0 in both modes ([The graphics scale does not follow the operation mode](../../../docs/reference/services.md#the-graphics-scale-does-not-follow-the-operation-mode)); on the iPhone and iPad it still answers tier 1 docked (X1.0's choice, for heat), so docked there the scene stays at 768x432 unless `DM_GFX_SCALE=0` is set (iOS not tested). Peppy's close-up 65 s into the intro has a mean luminance gradient (x1000 at 1080p) of 5.8 in console footage, 5.3 with tier 0 and 4.6 with tier 1. The sizes and gradients were measured on a build of the PR author's fork, not on `main`. Whether a console renders above 960x540 is not known.

## Driving it on the Mac

`python3 scripts/build_ipa_from_nsp.py <folder> --platform mac` builds the Mac shaders and the host and prints the run command. Headless, through `DM_CTL`: the title is up about 40 s after boot and `A` starts the game. The prologue cinematic follows, about 4 minutes on every run (a save holds no progress yet, and skipping it was not tried), then the tutorial's first question, about 300 s after boot: `LDown`, `A` answers no. Shots of the swap chain hold the picture in their top-left quarter. A `shot` takes about 165 ms: a hitch every few seconds in a run that takes them is the shot's.

## On the iPhone

The first was the first start after a fresh install, with no prewarm list in the app and an empty device archive; the second started from the first's `Documents/pso_user.tsv` and device archive. Both: thermal state 0 throughout, no audio underrun, and the five `[RED] nvnDeviceGetInteger` lines ([Open](#open)). The archive bundled with the app (73.6 MB) was taken (`holds the bases of every shader pair (16 of 16 probed bases found)`), so the `depth_mode zero` archive holds on the device too, and all 14 compute pipelines came from it, none built. Its lookups in play found nothing on the first start, as on the Mac: the bases the draws compiled are those of the render pipelines the device list records as `R` rows (the second start's prepare step found 358 of them in the device's archive), which the pair bases do not give.

### Pipelines on a first start

[`pso_manifest.tsv`](pso_manifest.tsv), the prewarm list the app ships, is that iPhone's own `Documents/pso_user.tsv` after the two starts: 999 rows, 542 shaders (`S`), 443 render pipelines (`R`) and 14 compute pipelines (`C`), in the order of first use; 929 from the first start, and the 70 (32 `S`, 38 `R`) the second start built that the first had not. `dm/tools/pso_seed.py` checked every row against [`shader_map.tsv`](shader_map.tsv), the profile's at `6448f757`, the commit the phone's build was made from (2,856 entries, as the log's `shader map 2856 entries`): none refused, none repeated, so nothing is left out.

- **What it changes:** a fresh install prepares the list before its first frame, so the first start's freezes (666 bases compiled in play, 46 frames over 100 ms with new pipelines, up to 2.1 s, 19.95 s of the submit thread waiting) move into the prepare step and the app's bundled archive. At the next build `pso_offline.py` compiles the `R` rows' layout bases into that archive ([Pipelines with a vertex layout compiled at a fresh install's prepare step](../../../docs/reference/shaders.md#pipelines-with-a-vertex-layout-compiled-at-a-fresh-installs-prepare-step)): its plan for `applegpu_g19p` (`--script-only`, this list, the X1.0 libraries) gives 399 layout bases for the 443 rows, none left out (44 rows share a base with another), beside the 1,483 pair bases and 68 compute pipelines.
- **Its cost on a fresh install** (an estimate, not measured): the prepare step takes the 399 bases from the app and loads the 542 libraries. On this phone the second start's 358 archive lookups took 0.43 s of thread time and its 405 specializations 13 ms, and a base from the app is not captured again for the compaction, so about 1 s. If the app's archive does not serve them (not measured on a device yet), the step compiles them: at 7.6 ms a base (Xenoblade Chronicles: Definitive Edition's measured prepare step) to 16.5 ms (this phone's 99 ms of compile time a base in play, over 6 workers), about 3-7 s. Most of the second start's 5.12 s was the compaction capturing 313 bases again from the first start's 31 files (28.8 s of thread time), which a fresh install with the list does not do for bases it takes from the app.
- **In play after it:** as the second start or better, since its 70 rows are in the list too. Places past the start of Corneria still build their pipelines at their first draw, and `pso_user.tsv` records them.
- **The settings:** handheld and Picture Stretch change no row: the stretch is the host's present, and a row's pipeline key (`pso_skey`) holds no picture size. Docked play was not recorded, so whether it draws other pipelines is not known.
- **The build:** the next build of this game runs the shader step again (its key covers the profile's files, `pso_manifest.tsv` among them), and `pso_offline.py` compiles 4 of its 5 compute groups again (the 14 `C` rows put those shaders first) and the 7 new layout groups; the 2 groups of pair bases are reused, and the stamp (`prebuilt.tsv`) is unchanged, since the pairs are. No game build was run for this change. No other game's build changes.

## Found on this game

- [Offline pipeline archive and profile depth disagree](../../../docs/reference/shaders.md#offline-pipeline-archive-and-profile-depth-disagree): the profile had no `depth_mode`, so a 0.5 Mac app (M4 Max, `applegpu_g16s`) carried an archive made for near = −w, and the host refused it (`made for … depth near=-w … this run needs … depth near=0`): its first start built all 1,483 pairs' bases itself (6.3 s, the first frame at 6.6 s). With `depth_mode zero` the app rebuilt from the same build folder (only the archive's 1,483 bases compiled again, 12 s; shaders, rewrite and host libraries unchanged) is taken: `holds the bases of every shader pair (16 of 16 probed bases found)`, no prebuild, the first frame at 1.4 s. On the same headless route (title, prologue, the tutorial's ring course, about 11 minutes) the draws still compiled 346 bases in play, as before, with 0 archive lookups found in both runs: the bases they wait for are not the ones the archive or the prebuild holds ([Open](#open)). The prologue's longest frames were 4.0, 1.2, 0.9 and 0.8 s (against 5.9, 2.0, 1.1 and 0.7 s), with the Mac under a load average near 30 from other builds, so their lengths are not comparable; the counts are. The iPhone archive (`applegpu_g19p`, `dm/ios/tools/build_ipa.sh`) takes the depth from the same key and would have been refused the same way; with the key it holds `main0_z` entries (planned with `--script-only`, not run on a device).
- [SDK 21 socket initialization and overloads](../../../docs/reference/services.md#sdk-21-socket-initialization-and-overloads) and [Socket `Poll` and `Select` with nothing to wait on](../../../docs/reference/services.md#socket-poll-and-select-with-nothing-to-wait-on): the game's HTTP thread aborted on a failed `poll`.
- [SDK 21's OutputStream on a virtual output device](../../../docs/reference/audio.md#sdk-21s-outputstream-on-a-virtual-output-device) and [SDK 21's hardware Opus decoder manager](../../../docs/reference/audio.md#sdk-21s-hardware-opus-decoder-manager): its voice and music.

## Open

- Draws compile their pipeline bases in play (346 on the route with 0.5's host, the graphics scale at tier 1 docked, the prologue's 0.6 to 4 s frames among them) although the app's archive holds a base for every shader pair: `archive lookups found 0`, `misses with no pulling base ready`, `draws with a hybrid pipeline 0`. Why their lookups miss is not known. The iPhone's first start (X1.0, handheld) had the same counters with 666 bases compiled in play; the second start found 358 of those bases in the device's archive as the prepare step built its list's `R` rows, so they are the bases of render pipelines the device list records, which the shipped list now has `pso_offline.py` put in the app's archive as layout bases ([Pipelines on a first start](#pipelines-on-a-first-start)).
- [The picture](#the-picture): the 3D stayed at 768x432 docked because the host answered graphics scale tier 1 there; the host now answers tier 0 on the Mac, which gives 960x540 (measured on a build of the PR author's fork, not on `main`); on the iPhone and iPad it keeps tier 1 docked, so 768x432 there unless `DM_GFX_SCALE=0`. Whether a console renders above that is not known.
- `[RED] DLSS: the game's bias mask (a reactive mask for MetalFX) is not passed on`.
- The game's wake-up eventfd fails (the host refuses `nn::socket::EventFd`), so its HTTP thread polls without a wake-up; harmless offline.
- A fresh install with the 999-row prewarm list on the iPhone, estimated at about 1 s of prepare step (3-7 s if the app's archive does not serve the layout bases; [Pipelines on a first start](#pipelines-on-a-first-start)): its `pipeline prepare` line should count about 399 layout bases from the archive bundled with the app and almost none compiled, and play to the same place should have none of the first start's freezes.
- `[RED] nvnDeviceGetInteger` items 0x62, 0x7d, 0x87, 0x99 and 0x9a: NVN2 reads them from the GPU at run time, and the host returns 0 for each (five lines at every start on the iPhone). What the game does with them is not known; nothing in the two runs points at them.
- `render_cond` not tried; the later levels and combat not tested; on the iPhone, docked play not tested.
- Mario Kart World 1.8.0 has not been run with the camera answers changed for this game.
